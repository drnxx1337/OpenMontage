## Findings

### HIGH — legacy resume is read-permissive and write-strict: the reader reports stages the writer then refuses

`File: lib/checkpoint.py:627-631` (new leniency) vs `lib/checkpoint.py:321-327` (`_enforce_stage_prerequisites`, unchanged).

`get_completed_stages` now accepts a checkpoint whose `pipeline_type` is `None`/`''`/`'unknown'` under a *named*
scope, so `get_next_stage` hands the agent a real resume point. `write_checkpoint` for the next stage then runs
`_enforce_stage_prerequisites`, which still requires `checkpoint["pipeline_type"] == pipeline_type` exactly, so every
legacy predecessor is classified `incomplete` and the write hard-fails.

Reproduced (`tmp_path`, legacy checkpoints written without `pipeline_type`, advanced under the real `cinematic` manifest):

```
legacy types: ['unknown', 'unknown']
scoped completed: ['research', 'proposal']
scoped next: script
ADVANCE: CheckpointValidationError -> PREREQUISITE VIOLATION: stage 'script' cannot advance;
         incomplete or missing: ['research', 'proposal'].
```

Net effect: a legacy project is told "research and proposal are done, resume at script" and can then never advance —
the exact case `5e7731e` set out to support. The new test does not catch it because
`tests/lib/test_checkpoint_resume_identity.py:47-60` stops at `get_next_stage` and never writes the next stage.
This is reachable in production: `scripts/backlot_simulate_run.py:85-86` and `scripts/backlot_screenshot_stage.py:179-180`
always pass `pipeline_type="cinematic"`, and `skills/meta/checkpoint-protocol.md:59` tells agents to always pass it.

Fix: apply one rule on both sides. Either let `_enforce_stage_prerequisites` treat `None`/`''`/`'unknown'` predecessors as
legacy (same predicate, one helper), or drop the read-side leniency and make resume surface "legacy project: re-scope the
checkpoints before advancing" instead of a next stage. Either way the resume test must write the next stage, not just
compute it. Confidence: **high (reproduced).**

### MEDIUM — the new `estimate_cost` warning fires on `PriceQuoteRequired`, a designed control-flow signal

`File: lib/scoring.py:430-441`, with `tools/provider_pricing.py:4-7` and e.g. `tools/audio/gemini_tts.py:95-99`.

`PriceQuoteRequired(ValueError)` is raised *on purpose* by 16 in-tree tools (`grep -c "raise PriceQuoteRequired" tools` = 16);
it means "this provider needs an account-specific quote", not "pricing blew up". The bare `except Exception` now logs
`estimate_cost failed for tool …` at WARNING for all of them on every scoring pass. Because `rank_providers`
(`lib/scoring.py:595`) scores a candidate list, one selector call can emit several of these.

Reproduced on a real tool:

```
WARNING lib.scoring: estimate_cost failed for tool gemini_tts: Gemini TTS requires a current token-based price quote
        — scoring cost at the neutral 0.50 instead of 0.0
cost_efficiency: 0.5 weighted: 0.475
```

Fix: `except PriceQuoteRequired:` → score neutral at `debug`/`info` (or record an `unknown_pricing` reason on
`ProviderScore`); keep WARNING for genuine failures. The new test (`tests/tools/test_scoring.py:52-66`) pins only the
genuine-failure text, so nothing guards the noisy branch. Confidence: **high (reproduced).**

### MEDIUM — "neutral" 0.5 is not neutral against the priced bands

`File: lib/scoring.py:443-448` vs `lib/scoring.py:274-291`.

`_compute_cost_efficiency` returns `0.1` when cost > 50 % of budget, `0.5` for 20–50 %, `0.8` below that, `0.0` over budget.
An unpriced tool's `0.5` is therefore indistinguishable from "costs 20–50 % of the remaining budget" and strictly *beats*
any tool known to consume > 50 % of budget (0.1) or to overrun it (0.0). Over `cost_efficiency`'s 0.10 weight
(`lib/scoring.py:51`) that is a 0.04 weighted swing — enough to reorder near-ties, in the direction of the tool nobody
can price. The previous review (`docs/reviews/merge-2026-10-30-py.md:66`) suggested an explicit `unknown_pricing` marker;
that was not adopted, so the ambiguity lives in the score itself. Confidence: **high (arithmetic from code)**; whether to
add the marker is a product call.

### LOW — the rationale comment at `lib/scoring.py:19-21` inverts the history

`# 0.0 read as "free" and won every ranking; 1.0 would be a lie.` At the point this constant is used,
`cost_efficiency=0.0` is the *worst* score (`lib/scoring.py:274-275`: "Free is 1.0, over-budget is 0.0"); the "free and
won" outcome belonged to the older `estimated_cost = 0.0` bug (an estimate of zero maps to 1.0), not to
`cost_efficiency = 0.0`. The real regression from the merge was "unpriced tools are penalised as maximally expensive".
As written, the comment will lead the next maintainer to invert the scale. Confidence: **high.**

### LOW — the docstring promises a "missing" `pipeline_type` case that cannot be read

`File: lib/checkpoint.py:614-618` vs `lib/checkpoint.py:188-191` and `schemas/checkpoints/checkpoint.schema.json:7`.

The schema lists `pipeline_type` under `required`, so a checkpoint file without the key fails validation before the new
`recorded_type is None` branch is ever reached — and the `CheckpointValidationError` propagates out of
`get_completed_stages` (no `try/except` there), so such a file crashes resume instead of falling back. Reproduced:

```
read FAILED: CheckpointValidationError Checkpoint failed schema validation: 'pipeline_type' is a required property
```

In practice the reachable legacy values are `'unknown'` (what `write_checkpoint` writes, `lib/checkpoint.py:507`) and `''`
(hand-written; verified accepted). Fix: narrow the docstring, or treat a schema-missing `pipeline_type` as legacy too if
pre-schema files must resume.

### LOW — `"unknown"` conflates "pre-scoping" with "caller forgot the scope"

`File: lib/checkpoint.py:507` with `lib/checkpoint.py:444-454`.

`write_checkpoint` stores `pipeline_type or "unknown"` whenever the caller omits the keyword argument and no
`project.json` marker supplies it. Under the new reader, such a *new* checkpoint counts as legacy for **every** scoped
pipeline — reopening the cross-pipeline reuse hole in a different shape. Named types still match exactly, so the
`test_pipeline_switch_restarts_shared_stage` case is safe; the exposure is only unscoped writes. Consider a distinct
sentinel (`"legacy"`) written only when the file predates scoping, or refuse to write `"unknown"` when a marker exists.

### LOW — module comment still calls websockets an "optional extra" after `setup.py` made it required

`File: tools/audio/_realtime_session.py:11-15` vs `setup.py:18` and `requirements.txt:18` (both `websockets>=14.0`), and
`tools/audio/realtime_audio.py:25` (`dependencies = ["python:websockets"]`, a soft dependency).

The batch did both halves of the previous review's advice (`docs/reviews/merge-2026-10-30-py.md:42`), so what remains is
an install-policy contradiction: the comment says optional extra, the packaging says hard requirement. Say "declared, but
tolerated missing at import time so one absent transport cannot disable the registry". Confidence: **high.**

### LOW — the patched tests now require websockets at `monkeypatch.setattr` setup

`File: tests/tools/test_provider_oct23.py:398`, `tests/tools/test_provider_oct23.py:424`.

`monkeypatch.setattr("websockets.sync.client.connect", …)` imports `websockets.sync.client` to resolve the target, so in the
"dependency absent" environment the contract test simulates, these two realtime tests fail at fixture setup rather than on
behaviour. That is not a regression (the old target `tools.audio._realtime_session.connect` also required an importable
websockets) and `requirements-dev.txt` pulls it in, but it means the suite as a whole cannot run dep-free. If that matters,
import the module and patch the attribute object, skipping when `importlib.util.find_spec("websockets") is None`.

### INFO — `importlib.reload` splits the class identity

`File: tests/contracts/test_realtime_optional_dep.py:33-37`, with `tools/audio/realtime_audio.py:10`.

Reloading `tools.audio._realtime_session` rebinds `RealtimeAudioSession` in that module while `realtime_audio` keeps the
pre-reload class object. No `isinstance` check on the session exists today, so nothing breaks; a future one would see two
distinct classes. `multiprocessing`/pickling of the session would be the first thing to fail.

### INFO — a missing-dep failure leaves the minted Eleven secret in `self.headers`

`File: tools/audio/_realtime_session.py:130-156`.

`__enter__` raises out of `_connect` (`:141`) before `self.socket` is set, so `__exit__` (which clears `self.headers`) never
runs and the freshly minted bearer token stays in the abandoned object. Identical to any pre-existing connect failure, so
not introduced here — but the missing-dependency path is now the most likely failure on a fresh install.

## What is verified clean

   (`tools/audio/_realtime_session.py:19-25`) imports `websockets.sync.client.connect` on first call and raises
   `RuntimeError(WEBSOCKETS_REQUIREMENT)` **`from`** the `ImportError` (`:24`), so `__cause__` is an `ImportError`; the
   message names the package, the floor and the exact `pip install` line (`:16`). The only production call site is updated
   (`:141`). `grep` finds no surviving reference to the deleted symbol (`_realtime_session.connect`, `import connect`) in
   `tools/`, `lib/`, `scripts/`, `backlot/`, `tests/`, docs or `.agents/` — `realtime_audio.py:10` imports the class, which
   still exists. End-to-end: `ToolRegistry().discover()` returns 155 tools with `websockets` blocked.
2. **The contract test really simulates absence.** `tests/contracts/test_realtime_optional_dep.py:20-31` replaces
   `builtins.__import__` for `websockets` and submodules; the reload in `:34` executes the module body under that fixture, and
   the *same* fixture applied to the pre-fix module raises `ImportError`, so the test fails on regression rather than passing
   vacuously. `:40-47` asserts message, install hint and the chained `ImportError`.
   (`assert reloaded.WEBSOCKETS_REQUIREMENT == WEBSOCKETS_REQUIREMENT` at `:37` is a tautology — same module object — and adds
   nothing; harmless.)
3. **`7ef0d05` retargets the real symbol.** `websockets.sync.client.connect` is what `_connect` resolves at call time, so the
   patch takes effect through the `from`-import; the old target no longer exists (`hasattr(module, "connect") is False`), which
   is why the pre-patch version of these two tests failed with `AttributeError`. Line 66 of the same file already used this
   pattern for `ElevenLabsTTS._turbo_audio` (`tools/audio/elevenlabs_tts.py:390`), so the file is now internally consistent.
4. **Checkpoint scoping on the typed path.** `tests/lib/test_checkpoint_resume_identity.py:12-33` still holds: a `cinematic`
   `research` checkpoint is rejected under `framework-smoke` (`get_next_stage` → `research`) and a matching `framework-smoke`
   checkpoint is retained (→ `script`). No typed data crosses pipelines.
5. **Scoring happy path.** `UNKNOWN_COST_EFFICIENCY` is used only in the `estimate_cost is not None` false branch
   (`lib/scoring.py:443-448`), and no in-tree `estimate_cost` returns `None` (AST scan of 93 overrides: zero `return None`),
   so the constant applies only to the exception path. A free tool still scores `cost_efficiency=1.0` (verified:
   `weighted_score=0.7525`), and priced tools go through `_compute_cost_efficiency` unchanged. The warning names the tool and
   the exception (`lib/scoring.py:434-440`), and `tests/tools/test_scoring.py:63-66` pins both.

## Bottom line

`0fddca4`, `17f033e` and `7ef0d05` are correct and adequately tested; the two scoring MEDIUMs are about signal quality
(`PriceQuoteRequired` noise) and the semantics of "neutral", not about the arithmetic. `5e7731e` must not land as is: it makes
a legacy project look resumable and then rejects the resume write, and its new test certifies only the read half.
